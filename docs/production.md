## Decisions

### Container and process

| Topic               | Decision                                                                                                                                                                                                                                                                   | Why                                                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Dockerfile          | Keep the two stages (`deps` with `npm ci --omit=dev`, runtime on `node:24-slim`, `USER node`). Add `HEALTHCHECK` running `node bin/healthcheck.js`, `EXPOSE 3000`, `STOPSIGNAL SIGTERM`. Add a `.dockerignore` (`node_modules`, `.git`, `test`, `docs`, `.env*`, coverage) | Small image without dev tools; Docker and orchestrators see health |
| Health check script | `bin/healthcheck.js` reads `ISSUER` and `PORT`, requests `http://127.0.0.1:<PORT><issuer path>/health` with a 3 s timeout, exits 0 on `200`, else 1. No dependencies beyond Node                                                                                           | The issuer path prefix is part of every route                      |
| Shutdown            | `src/server.js` handles `SIGTERM` and `SIGINT`: stop the key-reload timer and the job scheduler, close the HTTP server (wait at most 10 s for open requests), end the pool, exit 0. A second signal exits at once                                                          | Clean restarts during deploys                                      |
| Logging             | Unchanged (`pino` to stdout). Jobs log one line per run with counts                                                                                                                                                                                                        |                                                                    |

### Health

| Topic  | Decision                                                                                                                                                                                     | Why                                                          |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Path   | `GET <issuer>/health`, no auth, mounted before the provider callback, `Cache-Control: no-store`                                                                                              | Plan                                                         |
| Body   | `{ "status": "ok" \| "fail", "version": "<package version>", "checks": { "database": "ok" \| "fail", "signing_key": "ok" \| "missing" \| "fail" } }`. No error messages, hostnames or counts | Public endpoint; enough for a probe, nothing for an attacker |
| Checks | `database`: `SELECT 1` with a 2 s timeout. `signing_key`: an `active` key exists in `signing_keys` (`missing` if not; `fail` if the query fails). Next-key absence is not a failure          |                                                              |
| Status | `200` when both are `ok`, else `503`                                                                                                                                                         |                                                              |
| Code   | `src/health.js`: `createHealthRouter({ pool, version })`                                                                                                                                     |                                                              |

### Metrics

| Topic         | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Why                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Library       | `prom-client` with its own `Registry` (not the global one), default process metrics with prefix `tunnus_`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Standard; a private registry keeps tests independent                                  |
| Path and auth | `GET <issuer>/metrics`. Off (404) when `METRICS_BEARER_TOKEN` is empty. Otherwise `Authorization: Bearer <token>` compared in constant time (`crypto.timingSafeEqual` on SHA-256 digests); anything else `401` with `WWW-Authenticate: Bearer`                                                                                                                                                                                                                                                                                                                                                          | Plan                                                                                  |
| Counters      | Derived from audit actions in one place: `audit()` calls `metrics.countAuditAction(action, details)`. `tunnus_sign_ins_total` (`signin`), `tunnus_sign_ups_total` (`signup`), `tunnus_code_failures_total` (`code_failed`), `tunnus_mail_errors_total` (`mail_error`), `tunnus_rate_limit_hits_total{reason}` (`rate_limited`, label from `details.reason` when it is `email`, `ip` or `daily`, else `other`), `tunnus_admin_auth_failures_total` (`admin.auth_failed`), `tunnus_admin_requests_total` (other `admin.*`) , `tunnus_users_deleted_inactive_total`, `tunnus_inactive_warnings_sent_total` | Every event the plan names is already audited; counting there cannot miss a code path |
| Gauges        | Collected at scrape time with one query each: `tunnus_users{status}`, `tunnus_signing_key_age_seconds` (age of the active key), `tunnus_cleanup_last_success_timestamp_seconds` (from the job module's in-process state, `0` before the first run)                                                                                                                                                                                                                                                                                                                                                      | Alerts on stale keys and a stuck cleanup job                                          |
| Scope         | Counters are per process; with several replicas Prometheus sums them                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |                                                                                       |
| Code          | `src/metrics.js`: `createMetrics()` → `{ registry, countAuditAction, setCleanupSuccess, router({ pool, token }) }`. One instance per app, passed to `audit` through a module-level setter (`setAuditMetrics(metrics)` in `src/audit.js`) so existing `audit(pool, event)` call sites do not change                                                                                                                                                                                                                                                                                                      | No change to the many audit call sites                                                |

Audit action names are checked against the code (`src/web/interactions.js`,
`src/admin/`); if a name differs from the list above, the code's name wins
and this table is updated.

### Cleanup jobs

| Topic           | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                             | Why                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Schedule        | In-process scheduler: first run `CLEANUP_START_DELAY_SECONDS` after start (default 60) plus up to 60 s random jitter, then every `CLEANUP_INTERVAL_HOURS` (default 24). `CLEANUP_DISABLED=true` turns it off. Timers are `unref()`ed                                                                                                                                                                                                                 | Plan: daily; jitter spreads replicas                      |
| One runner      | Each run takes `pg_try_advisory_lock(<fixed key>)` on a dedicated client; if not acquired, the run is skipped and logged at debug                                                                                                                                                                                                                                                                                                                    | Several replicas, one cleanup                             |
| External run    | `tunnus-admin cleanup` runs all tasks once (migrations first, same lock) and prints counts as JSON on stdout                                                                                                                                                                                                                                                                                                                                         | For cron-driven deployments with `CLEANUP_DISABLED=true`  |
| Tasks, in order | 1. Delete `oidc_payloads` with `expires_at < now()`. 2. Delete `email_codes` with `expires_at < now() - interval '1 day'`. 3. Set `audit_events.ip = NULL` where `at < now() - AUDIT_IP_RETENTION_DAYS` and `ip IS NOT NULL`. 4. Delete `audit_events` older than `AUDIT_RETENTION_DAYS`. 5. Inactive-user warnings. 6. Inactive-user deletion. Each task is its own function and its own failure: one failing task is logged and the rest still run | Independent, testable steps                               |
| Batching        | Deletes and updates run in batches of 1 000 rows (`WHERE ctid IN (SELECT ctid ... LIMIT 1000)`) until fewer than 1 000 are affected                                                                                                                                                                                                                                                                                                                  | Short transactions on large tables                        |
| Zero            | `AUDIT_RETENTION_DAYS=0` and `AUDIT_IP_RETENTION_DAYS=0` disable that task (not "delete everything")                                                                                                                                                                                                                                                                                                                                                 | Same meaning as `INACTIVE_USER_DELETE_DAYS=0` in the plan |
| Result          | `runCleanup(...)` returns `{ payloads, codes, auditIpsCleared, auditDeleted, warned, warnFailed, deleted, errors: string[] }`; the run is audited as `cleanup.run` (no actor) with those counts, and a full success sets the metrics gauge                                                                                                                                                                                                           | Visible in audit and metrics                              |
| Code            | `src/jobs/cleanup.js` (tasks and `runCleanup`), `src/jobs/scheduler.js` (`startCleanupScheduler({ config, pool, mailer, logger, metrics })` → `{ stop() }`)                                                                                                                                                                                                                                                                                          |                                                           |

### Inactive users

| Topic          | Decision                                                                                                                                                                                                                                                                                                                                                                     | Why                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Inactive since | `coalesce(last_login_at, created_at)`                                                                                                                                                                                                                                                                                                                                        | A user created by an admin who never signed in is inactive from creation                                |
| Off switch     | `INACTIVE_USER_DELETE_DAYS=0` disables warnings and deletion                                                                                                                                                                                                                                                                                                                 | Plan                                                                                                    |
| Admins         | Users with `is_admin` are never warned or deleted automatically                                                                                                                                                                                                                                                                                                              | Avoids locking out the deployment; admins are few and handled by hand                                   |
| Warn           | Active users with `inactive_warned_at IS NULL` and inactive since before `now() - (DELETE_DAYS - WARN_DAYS) days`. Send the warning mail, then set `inactive_warned_at = now()`. A failed send leaves it `NULL` (retried next run) and is audited as `mail_error` with `details.kind = 'inactive_warning'`. Audited as `user.inactive_warned`                                | Plan: warning `WARN_DAYS` before deletion. The column exists (migration 002); sign-in already clears it |
| Mail cap       | Warning mails count against `MAIL_DAILY_CAP` (the same counter as sign-in mail, if it is a shared count; otherwise at most `MAIL_DAILY_CAP` warnings per run). When reached, stop warning for this run                                                                                                                                                                       | Mail provider limits                                                                                    |
| Delete         | Users inactive since before `now() - DELETE_DAYS` and either `status = 'disabled'`, or `inactive_warned_at <= now() - WARN_DAYS days`. Uses the same code path as the admin delete (revoke sessions, then delete the row). Audited as `user.deleted_inactive` with `target_id` only                                                                                          | Nobody active is deleted without a full warning period, even if the job did not run for a while         |
| Mail content   | New `buildInactiveWarningMail(config, locale, deleteOn)` in `src/mail.js`, texts in `fi`, `sv`, `en` in `src/i18n.js`, sent in `DEFAULT_LOCALE` (users have no locale). It says the account will be deleted on `deleteOn` (date only) unless the user signs in to any service that uses `BRAND_NAME` before then, has the controller footer, and links to the privacy notice | No link to click: Tunnus has no client of its own to sign in to                                         |

### Privacy notice

| Topic      | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Why                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| Path       | `GET <issuer>/privacy`. When `PRIVACY_NOTICE_URL` is set, `302` to it instead                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Plan                                          |
| Content    | Rendered server-side with the existing page layout and branding, in the locale from `?lang=fi\|sv\|en`, else `Accept-Language`, else `DEFAULT_LOCALE`. Sections: controller (`CONTROLLER_NAME`, `CONTROLLER_CONTACT`), data protection officer (`DPO_CONTACT`, section omitted when empty), what is stored, why (signing in to services), retention (numbers from the retention settings; deletion text omitted when disabled), processors (table from `PROCESSORS`), rights and how to exercise them (contact the controller) | Plan: nothing hard-coded about the controller |
| Processors | `PROCESSORS` (JSON) or `PROCESSORS_FILE` (path to JSON); setting both is a startup error. Each item `{ name, purpose, location }`, all non-empty strings. Invalid JSON or shape fails startup. Parsed in `loadConfig` as `config.privacy = { dpoContact, processors }`                                                                                                                                                                                                                                                         | Fail early on bad configuration               |
| Links      | Every end-user page footer links to the notice (`PRIVACY_NOTICE_URL` or `<issuer>/privacy`); the mail footers include the same link                                                                                                                                                                                                                                                                                                                                                                                            |                                               |
| Escaping   | All configured text is HTML-escaped with the existing helper                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Configuration is not trusted HTML             |
| Code       | `src/web/privacy.js`: `createPrivacyRouter({ config })`; texts in `src/i18n.js`                                                                                                                                                                                                                                                                                                                                                                                                                                                |                                               |

## Tests

- Unit: health status mapping; metrics auth (off, wrong token, right
  token) and counter mapping from audit actions; `PROCESSORS` /
  `PROCESSORS_FILE` parsing and errors; privacy page rendering (escaping,
  DPO section omitted, retention text when deletion is disabled, redirect
  with `PRIVACY_NOTICE_URL`); inactive-warning mail in three locales;
  healthcheck script URL building.
- Integration (real PostgreSQL): `/health` 200, and 503 with no active key;
  `/metrics` counts a sign-in done through the real flow; each cleanup task
  on seeded rows, including batching past 1 000 rows for one task; the
  warn → delete sequence with a fixed clock (inject `now`), sign-in clearing
  the warning, admins and recently active users untouched, a failed send
  retried; the advisory lock skipping a second concurrent run;
  `tunnus-admin cleanup` output.
